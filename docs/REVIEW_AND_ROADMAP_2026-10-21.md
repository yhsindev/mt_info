## 現有能力與主要缺口

Vite／React／TypeScript／MapLibre／Express 適合目前規模，不需換框架。來源 adapter、最後成功資料、更新／取消示警與本機 GPX 已有基礎。路況圖的空白主要來自缺少可確認的幾何，不是 MapLibre 無法繪製。

- `server/conditions.ts:70` 目前將所有步道經緯度保留 null，避免猜測未說明座標系統的入口 X/Y。
- `src/components/MapView.tsx:76` 已有路況點與 CAP 多邊形；尚未支援步道路線／受損路段，也沒有移動地圖後回傳視窗範圍的流程。
- 現有路況只含林業署管理範圍，不能代表雪霸／玉山／太魯閣所有高山路線。南二段尤其要補國家公園來源。
- `src/local-route.ts:5` 只保存路線名稱、二維分段與範圍；尚未保存高程、逐日節點、住宿、取水、撤退與留守計畫。這是新增功能的資料需求，不是既有 GPX 故障。

## 應先修的兩個問題

### P2 CAP 空白座標會被轉成零

位置：`server/cap.ts:16`。

`pair.split(',').map(Number)` 會把空字串轉成 0。以本機合成 XML 實際重現，輸入 `24,121 24,122 ,121`，得到含 `[121,0]` 的多邊形；若正式來源出現類似缺值，地圖範圍可能延伸到赤道。目前沒有證據顯示已接收的正式訊息曾觸發它。

改善：先驗證每個座標是非空合法數字字串，才轉數值；任一頂點無效便略過該幾何，保留文字區域。補測缺緯度、缺經度、非數字、退化多邊形與有效負數／小數。

### P2 離線後來源徽章不會自行過期

位置：`src/components/ConditionsPanel.tsx:26`、`src/hooks.ts:34`。

來源狀態只讀伺服器快照與 HTTP 錯誤。頁面已取得 ready／empty 後離線，輪詢會跳過；即使超過示警 5 分鐘、路況 1 小時，來源仍可能顯示「已取得／來源無紀錄」。頁面雖有離線提示，來源徽章沒有重新計齡。CAP 項目到期的前端過濾已存在，與這個來源新鮮度問題不同。

改善：建立與 `ageWeather` 同樣用途的 `ageConditions`，依 `checkedAt`、本機時鐘及各來源門檻呈現 stale，保留最後資料；將門檻放在共用設定或回應，避免前後端各寫一份。測試離線超時、空快照老化、恢復網路及重新取得。

本輪聚焦的路況與 GPX 相關 25 項既有測試通過，但不包含上述缺口；CAP 另以最小本機合成輸入重現。沒有因測試通過便認定以上情境已被覆蓋。

## 路況地圖的可落地設計

| 定位層級 | 地圖呈現 | 必須保留的意思 |
| --- | --- | --- |
| 官方災點／影響範圍 | 點、線段或多邊形 | 只有官方明確位置或經人工核實的區段才標成災點／受損段 |
| 公告涉及的步道 | 畫步道路線，附「此步道有公告」 | 公告可能只影響一小段，不能把全線染成實際崩塌範圍 |
| 步道入口參考 | 與災點不同的圖示 | 表示這條步道有公告，入口不是崩塌位置 |
| 只有行政區或文字 | 行政區相關公告／未定位清單 | 不在行政區中心補一個精確點，不默默隱藏 |

資料應增加幾何、定位層級、定位來源、查核日期、路線版本；事件類別、位置精度與資料新鮮度分開，不合成沒有校準依據的風險分數。

### 已核對的官方路線來源

1. 林業署[步道目錄](https://recreation.forest.gov.tw/mis/api/BasicInfo/Trail)、[異常路況](https://recreation.forest.gov.tw/mis/api/OpenStatus/Trail)以 TRAILID 對接；TR_POSITION 是位置文字，TR_SUB 是支線，里程通常散見 TITLE／CONTENT，現有 OpenStatus 沒有結構化災點經緯度。[正式來源與規範](https://recreation.forest.gov.tw/Service/OpenData)
2. [大霸官方步道頁](https://recreation.forest.gov.tw/Trail/RT?tr_id=027)公開 [KML](https://recreation.forest.gov.tw/Files/RT/GE/027.kml)，本輪實測有兩條線、五個點；頁面另有馬達拉溪登山口經緯度。可取得獨立的經緯度資料，不必猜入口 X/Y 的 CRS。
3. [大霸軌跡資料集](https://data.gov.tw/dataset/27000)及[正式檔案目錄](https://data.moa.gov.tw/api/FileToJson.ashx?DataId=438&DataTable=OpenDataList)的 KMZ 可下載；檔案 CreateDate 為 2020-07-24，目錄列每四年更新、政府資料開放授權第 1 版。目錄更新日不是路線測製日期，也不代表現地路徑沒有改線。
4. [能高西段資料集](https://data.gov.tw/dataset/38461)可見 TRAILID 欄位說明，但本輪取得的檔名寫 065，KMZ 內 TRAILID 卻是 64、URL 是 tr_id=064。不能單靠檔名前綴自動關聯；要核對檔內 ID、網址、名稱與官方目錄，不符就列待確認。
5. 玉山[南二段概況 PDF](https://www.ysnp.gov.tw/ckfinder/userfiles/files/%E5%8D%97%E4%BA%8C%E6%AE%B5.pdf)有 6.3–7K／12K 崩塌、23–24K 崩壁等區段文字，但文件內沒有可確認的發布日期。它能協助建立區段模型，不能直接作為「今天新發生」的事件。

建議採伺服器固定來源匯入、驗證及轉 GeoJSON，再按路線／視野載入。先做少量人工核實清冊，保存原始來源版本；不讓每位訪客移圖都重抓官方網站。

里程定位要確認起算點、行進方向、支線與路線版本。不能把「3K」依總長百分比放到任意 GPX，或忽略舊路／新路的差異。

### 移動地圖與清單聯動

- 提供「隨地圖範圍更新／查看全部」，在 moveend 後更新同一份結果；小資料量先於裝置內篩選。
- 用手機未被面板遮住的可視區判斷。點需落在視窗、線／面需與視窗相交，不能只用路線中心點判斷。
- 顯示「視窗內有公告的步道 N 條／公告 M 則」，另保留「位置待確認 K 則」。一條步道多段公告不應被當成多次獨立崩塌；來源未結構化時不顯示假精確的崩塌數量或面積。
- 點路線選卡片、點卡片定位路線；明確的「查看位置」動作可重複觸發，同一項重點也要有效。重疊圖徵需讓使用者選多筆。
- 手機保留單一圖層選單，把三層重複提示收成一個狀態入口；優先讓第一張摘要卡可見。沒有任何可定位結果時，文字清單優先，不讓空圖佔去大半畫面。

歷史崩塌判釋與崩塌潛勢可作以後的獨立背景圖，但要各自標示影像日期／年度與用途；不混成即時封閉事件。候選為[事件型崩塌目錄](https://data.gov.tw/dataset/177455)及[大規模崩塌潛勢區](https://data.gov.tw/dataset/176527)，本階段不優先加入。

## 登山計畫產生器

使用者範本的核心結構是：基本隊伍／日期、逐日路段與時間、日出日落、主線與備案、水源、山屋／營地、撤退與關門時間、留守通訊、菜單、公私裝備、審閱意見及參考紀錄。應轉成可編輯欄位和計算，不把長篇歷史文字直接複製進新行程。

| 區塊 | 可由工具協助 | 需要使用者確認 |
| --- | --- | --- |
| 逐日行程 | 選節點、分日、加總移動／休息／取水時間，檢查時程矛盾 | 隊伍速度、重裝／輕裝、支線取捨與預備日 |
| 距離與高程 | 由已確認的路線分段計算；保留來源與演算法說明 | 目前 GPX 模型沒有高程，先補解析／品質檢查；不能先產出無來源爬升 |
| 水源 | 整理來源類型、主／備取水點、取水往返時間、最後實際回報 | 當日有水與可取程度未知時保留未知；不從雨量推算水塔存量或水質 |
| 山屋與營地 | 名稱、位置、容量、設施、官方申請入口 | 容量不是空床；申請、抽籤與核准狀態分欄保存 |
| 撤退與備案 | 整理有來源的出口／路段，填入決策位置、時間與聯繫流程 | 實際可走性、過溪／崩壁、隊伍能力及決策由領隊審閱；不能以直線最近出口自動選路 |
| 留守與裝備 | 回報表、裝備分工、缺項及單位／數量檢查 | 私人聯絡資料僅放個人草稿／匯出，原範本的聯絡方式不進公開種子 |

第一版流程：選已驗證路線或匯入 GPX → 填日期／隊伍／每日停留點 → 補主備水源與住宿 → 填撤退／關門與留守 → 檢查待確認欄位 → 輸出可編輯 DOCX 與列印版。先做規則、表單與來源附錄，AI 可留待之後協助摘要／抽欄位；未知資料不補寫成事實。

範本中的每日水量不是所有行程通用預設值。工具可依使用者輸入加總個人、炊事與預備用水；不自動判定「帶這些就足夠」。醫療、藥物與通訊頻率等內容另採經確認的資料與人工審閱欄位，不沿用舊範本指示。範本內第三方路線圖也不直接內建公開產品，輸出地圖以有授權的來源或自己繪製的 GPX 圖為起點。

### 官方資料也要處理衝突

本輪 [玉山南營地介紹](https://www.ysnp.gov.tw/Trail/1783c684-3f87-4862-bf4e-e876e639d405?ID=7780f10e-4879-45bc-90ad-791bbf6b0094&Tab=3)標示開放，但[申請系統宿營地清單](https://hike.taiwan.gov.tw/bed_6.aspx)列容量 0 並註記暫不開放。這是來源衝突的實例，不能單純採最後下載的一頁，或把其中一筆當作已確認當日狀態。計畫書應保留兩個來源、查閱時間、待確認說明及使用者確認紀錄。

設施介紹可支援水源類型，但不是現時供水感測器。例如[拉庫音溪山屋介紹](https://www.ysnp.gov.tw/Trail/1783c684-3f87-4862-bf4e-e876e639d405?ID=010ce631-b297-4260-9de5-e3903f90343d&Tab=3)有溪流及設施說明；取水現況仍需有日期的回報。[一站式資料開放宣告](https://hike.taiwan.gov.tw/OpenData.aspx)允許註明來源後再利用並列第三方例外，但不等於所有資料都有穩定 API 或可直接重製各站圖片。

介面建議將既有 GPX 按鈕改成「路線／計畫」，開啟同頁側欄或手機全高面板，完成後回到原地圖狀態；不新增第五個圖層。先維持無帳號，草稿以本機保存／檔案匯入匯出為主，明確告知保存狀態。

## 建議執行順序與驗收

1. **修正與整理基礎**：補 CAP 空座標與來源離線老化，加入有意義的回歸測試；建立第一個 Git commit 及測試／編譯檢查。目前 git 尚無 HEAD，全專案仍未追蹤。再把 App 中資料查詢、路線與計畫狀態逐步拆成 hooks／元件，不必先大規模重構。
2. **完成路況地圖**：以大霸及另外 2–4 條無識別衝突的官方路線驗證；實作定位層級、路線／公告關聯、視窗篩選與手機摘要。驗收平移能更新清單、點圖與卡片互選、未知位置仍可查看、ID 不符不誤配、入口不標成災點、斷線可辨識過期。再擴充國家公園來源，支援南二段等路線。
3. **計畫草稿 MVP**：先用一條來源足夠的路線（例如大霸）完成可修改的逐日行程、水源備案、住宿與留守表；以本範本確定欄位，但不匯入其中的個資、歷史現況與第三方圖片。驗收修改日期／休息時間能一致更新時程、沒有確認的床位仍是未確認、來源衝突可見、草稿可恢復與匯出。
4. **公開部署前**：選定持久快取與單一更新排程的執行環境，驗證重啟／寫入失敗／服務停機後恢復；現有 scheduler 需程序運行，尚不能假設任意純靜態或多實例部署都可直接使用。

先把「找到地點 → 看見與這裡有關的公告 → 帶入自己的計畫」做順，比繼續增加互不相連的資訊圖層更符合目前的使用流程。
